# predict_stock

삼성전자(`005930.KS`)와 SK하이닉스(`000660.KS`)의 **다음 거래일 주가 방향·시초가예측**과 **1거래일·1주일·1개월 종가예측**을 만들고, 여러 머신러닝·딥러닝 모델을 동일한 시계열 검증 조건에서 비교하는 연구용 프로젝트입니다.

프로젝트의 중심은 Google Colab에서 위에서부터 순서대로 실행할 수 있는 [`samsung_direction_model_colab.ipynb`](samsung_direction_model_colab.ipynb) 노트북입니다. Yahoo Finance 시세와 KOSIS 월별 통계를 받아 특징 생성, 워크포워드 검증, 최신 예측, 결과 저장을 수행합니다. 월별 통계는 아래 API 키 또는 CSV 설정이 필요합니다.

결과는 Colab 런타임의 `/content/samsung_direction_outputs/`에 로컬 저장합니다. Google Drive 연결·인증 코드는 제거했습니다. 런타임이 종료·삭제되기 전에 `latest_outputs.zip`을 다운로드하여 보관하세요.

## ⚠️ 먼저 알아야 할 것: 이 모델이 실제로 예측하는 것

감사 결과, 종가→종가 타깃에서 측정되는 예측력의 **대부분은 "전일 종가 → 당일 시가" 갭**입니다.

| 구간 | 방향 판별 AUC | 의미 |
| --- | --- | --- |
| 갭 (전일 종가 → 당일 시가) | **약 0.80** | 전날 미국 반도체·나스닥·런던 GDR로 잘 맞힘 |
| 세션 (당일 시가 → 당일 종가) | **약 0.50** | 사실상 무작위 |

갭은 09:00 시가에 이미 가격에 반영되므로, **07:00 예측으로는 취할 수 없습니다.** 시가에 진입해 종가에 청산하는 — 실제로 가능한 유일한 거래 — 구간에서 모델이 지시한 방향의 일평균 수익은 거래비용 차감 전에도 0 근처이거나 음수입니다.

그래서 노트북 8절에 **갭/세션 분해 표**를 두어, 매 실행마다 "거래 가능한 예측력"이 얼마인지 직접 보이도록 했습니다. `balanced_accuracy`만 보고 성능을 판단하지 마세요 — 이 지표는 `VOL_BAND_MULT`를 키우면 단조 증가합니다.

이 저장소는 **연구·교육용**입니다. 투자 판단에 사용하지 마세요.

## 주요 기능

- 삼성전자·SK하이닉스 보고서 제목 바로 아래에 **한눈에 보는 쉬운 요약**을 자동 생성합니다. 방향·시초가예측·종가예측·중장기 전망·영업이익 추정·실제 예측 성적을 일상적인 말로 설명합니다. 별도 AI API나 토큰을 사용하지 않으며, 검증 근거가 부족한 가격은 숫자 대신 ‘예측하기 어렵습니다’로 표시합니다. 요약의 성적은 보고서 생성 시점 기준이고 이후 채점은 아래 ‘예측 vs 실제’ 절에서 확인합니다.
- 다음 거래일의 삼성전자 수익률을 `하락`, `보합`, `상승`으로 분류합니다.
  - 하락: 수익률 < -band, 보합: -band ≤ 수익률 ≤ +band, 상승: 수익률 > +band
  - `band`는 기본값으로 **최근 20일 일간 변동성 × 0.3**이며, 고정 ±0.5%로 바꿀 수 있습니다.
  - 타깃은 종가→종가(07:00 예측) 또는 시가→종가(09:00 시가 확정 후 예측) 중 선택합니다.
- **갭/세션 분해**로 예측력이 어느 구간에서 나오는지, 거래비용 차감 후 기대손익(bp)이 얼마인지 함께 보고합니다.
- **시초가예측**을 별도로 제공합니다. 1거래일 종가예측이 검증을 통과하는 이유는 거의 전부 갭이므로, 갭 자체를 같은 방법으로 예측해 원장에 `kind="open"`으로 남기고 시가로 채점합니다. 09:00 이전에만 의미가 있고, 시가에 매수해서 얻을 수 있는 수익이 아닙니다.
- 모든 성능 비교에 **월 블록 부트스트랩 95% 신뢰구간**을 붙입니다. 신뢰구간이 0을 포함하면 "동률"입니다.
- 1거래일, 5거래일(약 1주일), 20거래일(약 1개월) **종가예측**을 구간과 함께 제시합니다. 신호 선택 구간에서 기준선 대비 우위가 없으면 점 예측을 비우고 현재가 중심의 구간을 제공합니다.
- 원본 시세를 캐시에 저장합니다. 기본은 매 실행 새 데이터 수집이며, 고정 스냅샷 재현은 `USE_DATA_CACHE=True`로 선택합니다.
- 예측 결과를 로컬 저장 폴더의 `forecast_log.csv`에 누적하고, 다음 실행 때 실제값·방향 적중 여부·가격 오차를 CSV로 갱신합니다.
- 쉬운 요약 아래 **어제 예측 vs 실제** 절이 실제로 미리 낸 예측만 채점해 보여주고, 최근 20·60거래일 창의 방향 적중률·구간 적중률·수익률 MAE(vs 변화 없음)·실현 기울기(vs OOF 축소계수)를 집계합니다. 기준을 벗어나면 경고를 띄우지만 설정을 자동으로 바꾸지는 않습니다 — 하루 결과는 잡음이므로 판단은 60일 창으로 합니다.

## 보고서 상단의 생성 시각·코드 커밋

각 보고서 제목 아래에 **생성 시각(KST)** 과 **그 보고서를 만든 코드의 커밋**(짧은 SHA·제목·커밋 시각, 커밋 페이지 링크)이 표시됩니다. 보고서만 보면 "언제 만들었나"는 알아도 "무슨 코드로 만들었나"는 알 수 없어서, 고친 내용이 실제로 반영됐는지 확인할 수 없기 때문입니다. Actions는 `GITHUB_SHA`를, 로컬·Colab은 `git rev-parse HEAD` 또는 원격 브랜치의 최신 커밋을 씁니다. 커밋 정보를 못 받아도 보고서는 그대로 나옵니다.

## 한국 정부 API와 보관본 갱신

KOSIS·관세청은 해외 IP(GitHub Actions 러너)에서 연결 자체가 막히는 일이 잦습니다(`URLError`). 그래서 **한국에서 돌린 실행이 받은 값을 저장소 `macro_history/`에 남겨 두고, 자동 실행은 그것을 씁니다.**

Colab에서 노트북을 처음부터 끝까지 실행하면(보안 비밀에 `GITHUB_TOKEN`이 있으면) 보관본이 **자동으로 갱신**됩니다 — 선행지수·반도체 수출액·뉴스심리지수·외국인 수급 중 그 실행이 **직접 받은 것만** 올립니다(보관본을 보관본으로 덮어쓰지 않기 위해). 이 갱신은 원장·보고서 발행과 무관하므로, Colab 실행의 예측이 원장에 섞이지 않습니다. 끄려면 `PREDICT_STOCK_SYNC_MACRO=false`.

보관본이 45일 넘게 낡으면 보고서 상단에 "참고자료 보관본이 오래되었습니다"라고 표시되고, 100일 만료가 가까우면 그 사실도 함께 적힙니다. 월 단위 지표라 한 달에 한 번 정도 Colab에서 돌려 주시면 자동 실행이 계속 최신 값으로 돕니다. 보관본이 100일 넘게 낡으면 기존 만료 규칙이 해당 지표를 자동으로 제외하므로, 낡은 값이 조용히 계속 쓰이지는 않습니다.

## 되돌릴 수 있는 방법론 스위치 (2026-09-08)

두 가지를 바꿨고, 둘 다 노트북 설정 셀의 한 줄로 되돌릴 수 있습니다. 어느 쪽이 나은지는 사람이 판단하지 않고 **원장**이 답합니다 — 바꾸기 전 모델도 비교 행으로 매일 기록되기 때문입니다.

| 스위치 | 바꾼 값 | 이유 | 되돌리기 | 판단 근거 |
| --- | --- | --- | --- | --- |
| `SELECTION_METRIC` | `"log_loss"` (전: accuracy) | 확률 모형은 proper scoring rule로 골라야 합니다. accuracy로 고르면 다수 클래스만 맞히는 설정이 뽑혀 balanced accuracy가 떨어졌고, 실제로 고정 설정(`Previous ensemble`)이 더 나았습니다. | `"accuracy"` | 원장의 `Mean ensemble`(선택된 설정) vs `Previous ensemble`(고정 설정) 60일 쌍체 비교 |
| `HEADLINE_MODEL` | `"No macro ensemble"` = 시세만 (전: Mean ensemble = 전체 특징) | 월별 지표·뉴스심리·수급을 넣은 모델이 시세만 쓰는 모델보다 낫다는 근거가 아직 없습니다(쌍체 비교 모두 동률 이하). | `"Mean ensemble"` | 원장의 두 모델 60일 쌍체 비교. CI가 0을 배제하며 전체 특징 쪽이 나으면 되돌립니다 |

되돌릴 때는 설정만 바꾸면 됩니다. 원장은 모델 이름별로 쌓이므로 이력이 섞이지 않고, `config.json`에 어느 설정으로 만든 예측인지 남습니다.

## 자동 실행이 멈추면 어떻게 아는가

워크플로가 **초록불로 끝나면서 아무것도 하지 않는** 일이 실제로 있었습니다(2026-09-08: 지운 스텝을 참조하는 `if` 조건 때문에 채점이 하루 종일 건너뛰어졌습니다). cron 누락도 커밋 이력을 사람이 뒤져야 알았습니다. 그래서 두 가지를 두었습니다.

- **감시 잡**(평일 09:20 KST): 오늘 사전 예측이 원장에 있는지만 봅니다. 없으면 **일부러 실패**해서 GitHub 실패 알림이 오게 합니다(`tools/check_ledger_health.py`). 주말·연휴로 며칠 비는 것은 정상으로 보고, 4일을 넘기면 실패로 봅니다.
- **노트북 전체 실행 테스트**(`tests/test_notebook_smoke.py`): 가짜 시세로 전 셀을 끝까지 돌려 보고서·원장이 생기는지 확인합니다. 셀 순서나 변수 이름이 어긋나는 오류는 실행해야만 잡힙니다. 1~2분 걸리며 `PREDICT_STOCK_SKIP_SMOKE=1`로 건너뛸 수 있습니다.

## 실행 시각

코드가 바뀌어 `main`에 push되면(노트북·`tools/**`·헬퍼 모듈) 일일 보고서가 **자동으로 다시 만들어집니다**. 이때는 보고서만 새로 발행하고 원장에는 예측을 기록하지 않습니다 — 원장은 날짜별 최초 사전 예측만 집계하므로, 아무 때나 밀어 넣으면 그날의 공식 기록이 바뀌기 때문입니다. `docs/`·`forecast_history/` 커밋은 경로 필터로 제외해, 보고서가 만든 커밋이 다시 실행을 부르지 않게 했습니다.

| 워크플로 | 시각(KST) | 하는 일 |
| --- | --- | --- |
| 일일 보고서 | 평일 06:22 · 07:25 · 그리고 3시간마다 | 그날의 **확정 예측**을 만들어 원장에 기록하고 보고서를 발행합니다. 전날 밤 미국 시장 정보가 들어 있습니다. GitHub의 cron은 `:00`·`:30`에 요청이 몰려 크게 밀리거나 통째로 건너뛰므로(2026-09-08 06:30 예정 실행은 실행 흔적조차 없었습니다) 붐비지 않는 분에 걸고 한 시간 뒤 백업을 하나 더 둡니다. 3시간 간격(09:22·12:22·15:22·18:22·21:22·00:22·03:22) 회차를 더 두어, cron이 밀리거나 건너뛰어도 그날 안에 한 번은 돌게 했습니다. 이 회차들은 `tools/should_run_today.py`가 판단해 대부분 몇 초 만에 끝납니다 — 09:00 전에는 "오늘의 사전 예측"이 있으면, 09:00 후에는 "오늘 기록"이 하나라도 있으면 넘어갑니다(그 시각 이후에는 무엇을 만들어도 사전 예측이 될 수 없으므로). 금·은·중국·관심도·영업이익은 06:22 회차에만 돌고, **검색어만 3시간마다 새로 만듭니다** — 하루 사이에 실제로 바뀌는 유일한 보고서이기 때문입니다. |
| 시초가 확인 | 평일 09:37 | 개장 직후 시가가 확정되면 **시초가 예측만** 채점해 해당 절을 갱신합니다. 종가 항목은 그대로 두고 마감 후에 채웁니다. |
| 장 마감 후 갱신 | 평일 16:10 | 그날 종가로 예측을 **채점**하고 보고서의 '어제 예측 vs 실제' 절만 바꿔 끼웁니다(`tools/build_afternoon_update.py`, 1분). 워크포워드는 다시 돌리지 않습니다 — 아침에 이미 했고 하루 사이에 달라지지 않으며, 오후에 다시 계산하면 같은 날 보고서의 숫자가 아침과 미세하게 달라져 혼란만 남습니다. 새 예측도 만들지 않습니다: 오후에는 그날 밤 미국 장 정보가 없어 아침 예측보다 정보가 적은데, 원장은 날짜별 최초 사전 예측만 집계하므로 기록하면 정보가 적은 쪽이 채택되기 때문입니다. |
| 장기 전망 | 매달 7일 07:00 | 7절 조각을 다시 계산합니다. |

## G20 경기선행지수 (OECD CLI)

"G20 CLI가 한국 수출을 2개월 앞선다"는 차트는 최종 수정치로 사후에 그린 것입니다. CLI는 추세제거·평활 필터를 전체 시계열에 걸어 계산하므로 **매달 소급 수정**되고 발표는 참조월로부터 5~6주 뒤입니다. 그리고 수출을 앞서는 것과 주가를 앞서는 것은 다른 문제입니다 — 이 저장소의 측정으로는 주가가 수출을 앞섭니다. 그래서 CLI는 두 곳에서 **효과를 재는 용도**로만 씁니다.

- 장기 전망(7절): 특징에 넣고 같은 날짜에서 CLI를 뺀 모델과 MAE를 비교합니다.
- 다음 분기 영업이익 전망(8절): 선행지수가 이론적으로 맞는 자리입니다. 분기 t 중간에 t+1 영업이익을 내다보되, CLI 포함/제외 모델을 나란히 재고 기준선을 이길 때만 숫자를 냅니다.

참조월+1개월 20일 이후 값만 쓰지만 개정 문제는 남아 있어 백테스트는 낙관적입니다. 자료는 OECD 데이터 API에서 키 없이 받습니다(FRED에는 G20 집계가 없습니다 — G7·개별국만 있고 OECD 전체는 2022-11에서 끊겼습니다). FRED로 바꾸려면 `FRED_API_KEY`와 `FRED_CLI_SERIES_ID`(예: `G7LOLITOAASTSAM`)를 함께 지정합니다. 확인은 `python tools/probe_fred.py`.

## 합성 사이클 점수와 장단기 금리차 (장기 전망 7절)

"일평균 수출이 코스피와 상관이 높다", "금리차가 선행지수를 앞선다", "뉴스심리지수가 선행지수를 1개월 앞선다"는 관찰을 그대로 특징으로 더하지 않습니다. 12개월 지평은 독립 표본이 20여 개뿐이라 지표를 하나씩 더하면 계수만 늘어 과적합이 되고, 나아졌는지 판정할 검정력도 없기 때문입니다. 대신:

- **합성 사이클 점수 하나**: 일평균 수출 YoY(월 합계 ÷ 조업일수, 월+2 지연), 선행지수 3개월 변화, 뉴스심리 20일 변화(지수 날짜+14일), 장단기 금리차(국고채 10년−3년, ECOS 일별)를 각각 **확장 창 z-score**로 표준화해 가중치 없이 평균합니다. 학습되는 계수가 하나뿐입니다. 같은 날짜에서 점수를 뺀 모델과 MAE를 비교해 보고서에 표시합니다.
- **금리차는 국면표의 조건**으로도 씁니다. 같은 국면, 같은 개월째에 금리차가 역전이었던 구간과 정상이었던 구간의 잔여 기간을 나눠 보여 줍니다. 모델이 아니라 서술 통계이고, 금리차는 매일 나오고 소급 수정이 없어 조건으로 쓰기에 가장 깨끗합니다.

## 관세청 원천에서 수출액 직접 받기

KOSIS 품목별 월 확정치는 관세청 원천보다 2~5주 늦습니다. 공공데이터포털 **관세청_품목별 수출입실적**(`/1220000/Itemtrade/getItemtradeList`)에서 HS 8541(개별소자)·8542(집적회로) 수출액(`expDlr`, 달러)을 직접 받아, **KOSIS에 아직 없는 달만** 채웁니다. KOSIS 확정치는 그대로 둡니다.

쓰기 전에 겹치는 달의 배율 중앙값이 1 ±15% 안인지 확인하고, 벗어나면 사용하지 않습니다 — 품목 정의나 단위(천 달러)가 다르면 조용히 1000배 틀린 값이 들어가기 때문입니다. 보고서에는 어느 달이 관세청 원천에서 왔는지와 검증 배율을 적습니다. 인증키는 `DATA_GO_KR_KEY`(Encoding·Decoding 어느 쪽이든 동작).

## 관세청 수출 속보로 나우캐스트 앞당기기

관세청은 매달 11일·21일경 1~10일·1~20일 수출입 현황을 발표하고 반도체 증감률을 따로 적습니다. KOSIS 품목별 월 확정치는 그보다 2~5주 늦습니다. `macro_inputs/exports_flash.csv`에 `month,days,semiconductor_yoy`(예: `2026-09,20,0.31`)를 적어 두면 그 달을 **전년 동월 확정치 × (1+YoY)** 로 잠정 추정해 8절 나우캐스트에 한 달 먼저 넣습니다. 확정치가 KOSIS에 들어오면 속보는 자동으로 무시되고, 보고서에는 어느 달이 속보 기반인지 적힙니다. 관세청 API 형식이 확인되면 자동 수집으로 바꿀 수 있습니다.

## 영업이익 추정 원장과 잠정실적 채점

8절 추정도 원장(`forecast_history/<종목>/earnings_log.csv`)에 남기고 실제 영업이익이 나오면 채점합니다. **(분기, 반영 개월 수)마다 그 시점의 첫 추정만** 한 번 기록하고 이후 실행이 덮어쓰지 않습니다 — "7·8월만 알던 시점의 추정"과 "9월까지 알던 시점의 추정"이 각각 남아, 정보가 늘수록 정확해지는지 볼 수 있습니다.

채점 값은 두 곳에서 옵니다. 분기보고서(**확정치**)는 분기 종료 후 45일쯤 뒤에 나오지만, 두 회사는 일주일 안팎에 **영업(잠정)실적**을 공시합니다. 그래서 잠정실적 공시를 찾아 먼저 채점하고, 확정치가 나오면 그 값으로 다시 채점합니다(원장에 `actual_source`로 남습니다). 잠정치는 공시 본문 표를 읽어야 해서 불안정하므로 **단위를 못 읽거나 값이 직전 분기의 0.2~5배를 벗어나면 쓰지 않습니다** — 잘못 읽은 숫자가 원장에 들어가는 것보다 채점이 5주 늦는 편이 낫습니다.

## 이번 분기 영업이익 추정 (월간, 보고서 8절)

월별 반도체 수출액으로 삼성전자·SK하이닉스의 **진행 중인 분기 영업이익**을 나우캐스트합니다(`tools/build_earnings_forecast.py`). 주가 예측과 달리 미래를 맞히는 일이 아니라 이미 벌어지고 있는 분기의 결과를 발표 전에 추정하는 일이고, 메모리 영업이익과 반도체 수출액은 같은 것(D램·낸드 가격과 물량)을 재고 있어 여지가 실제로 있습니다.

- 분기가 끝나기 전이므로 **그 분기의 앞 k개월** 수출만 쓰고, 과거 분기도 똑같이 앞 k개월로 특징을 만들어 학습합니다(k = 이번 분기에 확보된 월 수). 과거는 3개월, 지금은 2개월로 두면 3개월 평균에 맞춰 학습된 계수를 성질이 다른 값(더 흔들리는 2개월 평균)에 적용하게 됩니다. 보고서에는 어느 달이 반영됐고 어느 달이 아직 KOSIS에 없는지 그대로 적습니다.
- KOSIS 품목별 수출 표는 관세청 속보보다 며칠~2주 늦게 갱신되므로 **매일** 확인합니다. 영업이익 이력은 저장소(`macro_history/operating_profit_<종목>.csv`)에 쌓아 두고 최근 2년만 다시 받아 DART 요청을 종목당 8건으로 줄였습니다.
- 특징: 원화 환산 수출 규모, 수출 전년 동기·전분기 대비, 직전 분기 영업이익, 4분기 전 영업이익.
- **기준선을 이겨야 숫자를 냅니다.** 워크포워드 MAE가 '직전 분기 그대로'와 '4분기 전 그대로'를 모두 이겨야 점 추정을 발표하고, 못 이기면 기준선과 구간만 보여 줍니다.
- 영업이익 이력은 [DART OpenAPI](https://opendart.fss.or.kr/) 인증키(`DART_API_KEY`)로 받거나 `macro_inputs/operating_profit_<종목>.csv`(`quarter,value`, 단위 원)로 넣습니다. DART는 누적 공시라 분기 값으로 차분해 씁니다.

## 장기 전망 (월간, 보고서 7절)

반도체 수출액과 선행지수 순환변동치가 **앞으로** 3·6·12개월 주가 수익률을 맞히는지를 2000년 이후 월별 자료로 검증하고, 결과를 삼성전자·SK하이닉스 보고서 맨 아래 "7. 장기 전망" 절에 붙입니다(`tools/build_longterm_report.py`, 매달 7일 07:00 KST 자동 실행). 수출액 추세와 주가 수준의 상관이 높다는 사실은 둘 다 우상향하기 때문이며 예측력의 근거가 아니므로, HP 필터 같은 양방향 추세는 쓰지 않고 그 시점까지의 자료로 계산한 지표(수출 YoY와 가속, 선행지수 수준·변화, 주가/수출액 비율 z-score, 모멘텀, 낙폭)만 씁니다. 겹치는 타깃은 워크포워드에서 h개월 purge하고, 점 예측은 0% 기준선을 이길 때만 냅니다. 이기지 못하면 사이클 국면(수출 YoY 부호 × 가속/감속)별 과거 12개월 수익률 분포와 지금과 비슷했던 시기만 보여 줍니다.

같은 절에서 **지금 사이클 국면이 얼마나 더 갈지**도 추정합니다. 과거 같은 국면 구간들의 기간에서 이미 지난 개월 수를 뺀 **조건부 잔여 기간**(중앙값·사분위)을 쓰는데, 전체 기간 분포를 그대로 쓰면 이미 지난 기간을 두 번 세게 되기 때문입니다. 한두 달 깜빡이는 전환은 국면으로 세지 않고(3개월 이상), 지금 구간이 과거 어느 구간보다 길면 "말할 표본이 없다"고 적습니다. 표본이 열 개 남짓이라 범위로만 읽어야 하고, 국면 판정 자체가 월+2 발표 지연을 반영해 실제 전환보다 늦게 인지됩니다.

## 공시 — 이벤트 표시와 참고 (예측 특징 아님)

DART 공시 목록을 매일 받되 **예측 특징으로 쓰지 않습니다.** 대형주는 공시가 몇 분 안에 가격에 반영되어 다음 날 07:00 예측에는 새 정보가 되지 않기 때문입니다. 대신 두 곳에 씁니다.

- **이벤트 표시**: 분기 종료 후 2주(실적 시즌)이거나 전날 잠정실적·배당·자사주·공급계약 같은 공시가 있었으면 원장의 `event_flags`에 남기고 보고서 1절 위에 "이벤트일" 안내를 띄웁니다. 예측 자체는 바꾸지 않습니다 — 구간을 임의로 넓히면 보정이 깨집니다. 표시가 쌓이면 이벤트일과 평일을 나눠 채점할 수 있습니다.
- **최근 공시 절**: 최근 10일 공시 제목·날짜·DART 링크. 예측이 빗나간 날 그 이유를 바로 볼 수 있습니다.

`DART_API_KEY`가 없으면 이 절만 빠지고 나머지는 그대로 돕니다.

## 외국인·기관 수급 (보고서 '외국인·기관 수급' 절)

삼성전자·SK하이닉스는 외국인 비중이 절반 안팎이라 그들의 순매수 방향과 주가가 같이 움직입니다. 다만 "같이 움직인다"와 "앞선다"는 다릅니다. 투자자별 거래 실적은 그날 장 마감 뒤 확정되므로 07:00 예측에는 **전일까지**만 들어가고, 이 절이 재는 것은 "전일까지의 순매수가 다음 날 방향을 맞히는가"입니다. 특징(전일 순매수÷20일 평균 거래량, 5·20일 누적, 연속 순매수 일수, 기관 5일, 외국인 지분율 20일 변화)을 넣은 모델과 뺀 모델(`No flow ensemble`)을 같은 날짜에서 쌍체 비교해 표시합니다.

보고서에는 최근 1·5·20·60일 외국인·기관 순매수(주식 수, 대략의 억원), 연속 순매수 일수, 외국인 지분율과 20일 변화, 60거래일 외국인 누적 순매수 vs 종가 그림이 나옵니다.

자료원은 KRX 정보데이터시스템(`pykrx`, 로그인이 필요해져 `KRX_ID`/`KRX_PW` Secrets 필요) → 네이버 금융 매매동향 페이지(계정 불필요) → 저장소 보관본 순입니다. 성공한 자료는 `macro_history/investor_flows_<코드>.csv`에 쌓아 두고 최근 60일만 다시 받습니다.

## 뉴스심리지수 (한국은행 ECOS, 선택)

`USE_NSI_FEATURES=True`가 기본값입니다. 한국은행 뉴스심리지수(일별)를 ECOS Open API로 받아 수준(−100), 5일·20일 변화, 60일 z-score 네 특징을 만듭니다. 지수는 일별로 작성되지만 **공개는 주 1회(2026-09부터 매주 월요일 16:00)** 이므로, 미래 정보가 섞이지 않도록 **지수 날짜+14일 이후에만** 사용합니다(2026-09-08 확인 시 9/7 공개분이 8/31까지였음). 한은이 말하는 "1개월 선행"은 소비자·기업심리지수에 대한 선행이지 주가에 대한 선행이 아닙니다. 효과는 매 실행 `Mean ensemble − No NSI ensemble` 쌍체 비교(95% CI)로 측정하며, CI가 0을 배제하기 전에는 채택 근거로 보지 않습니다.

설정: [ECOS Open API](https://ecos.bok.or.kr/api/) 인증키를 발급받아 Colab 보안 비밀 / GitHub Secrets에 `ECOS_API_KEY`로 등록합니다. 못 받으면 그 지표만 빼고 계속 진행합니다(KOSIS와 달리 `MACRO_STRICT`의 대상이 아님). 2026-09-01 신(新)지수로 통계표 코드가 바뀌었을 수 있으니, 조회가 실패하면 `python tools/probe_ecos.py`로 코드를 확인하고 `ECOS_NSI_STAT_CODE`, `ECOS_NSI_ITEM_CODE` 환경변수로 넘기세요. CSV로 쓰려면 `macro_inputs/news_sentiment.csv`(`date,value`)를 둡니다.

2. Colab 왼쪽 열쇠 아이콘 **보안 비밀**에 이름 `KOSIS_API_KEY`, 값에 본인 키를 넣고 노트북 접근을 허용합니다. 채팅·노트북 코드에 키를 쓰지 마세요. 로컬에서는 같은 이름의 환경변수를 사용합니다.
3. 노트북 전체를 실행합니다. KOSIS 공식 API로 두 통계의 과거 2년 준비 구간부터 최신 월까지 조회합니다. 키와 인증 URL은 출력물에 저장하지 않습니다.

API 대신 CSV를 사용하려면 로컬 저장 폴더의 `macro_inputs/`(Colab 기본값: `/content/samsung_direction_outputs/macro_inputs/`)에 `leading_cycle.csv`, `semiconductor_exports.csv`를 저장합니다. 해당 파일이 있으면 API보다 우선합니다. KOSIS에서 정확한 항목 하나와 충분한 과거 기간을 선택하고 **시점을 열**로 내려받은 CSV를 지원합니다. 복잡한 다중 헤더 형식은 아래 형식으로 정리하세요. 반도체 `value` 단위는 **달러**입니다(천 달러·백만 달러로 받은 경우 환산 필요).

```csv
month,value
2025-01,100.1
2025-02,100.2
```

위 숫자는 형식 예시입니다. 실제 학습에는 공식 통계 값을 사용하세요. 최소 `START_DATE`보다 2년 이전부터 최신 월까지 준비해야 합니다. 파일을 사용하는 경우 새 월이 발표될 때 파일도 갱신해야 합니다. 키나 자료가 없으면 설정 안내와 함께 중단하며, 조용히 두 지표를 빼지 않습니다. 기존 시세 모델만 쓰려면 명시적으로 `USE_MACRO_FEATURES=False`로 설정합니다.

**발표 시점과 수정치:** 실제 발표 이력이 있는 CSV에는 `released_at`을 추가합니다. 한국 시각 07:00 예측(시가 기준 모드는 09:00)까지 공개된 값만 사용하며, 이후 수정된 값으로 이전 날짜의 특징을 다시 계산하지 않습니다. 같은 월의 수정치는 새 행으로 추가합니다. `vintage`, `source` 열도 캐시·스냅샷에 보존합니다.

```csv
month,value,released_at,vintage,source
2025-08,100.1,2025-09-01T10:00:00+09:00,initial,official_release
2025-08,100.2,2025-10-01T10:00:00+09:00,revised,official_revision
```

위 값과 날짜는 **형식 예시**입니다. `released_at`에는 해당 행의 수치가 실제로 공개된 발표/수정 시각과 시간대를 넣어야 합니다. 날짜만 있는 값, 시간대 없는 값, 월이 끝나기 전의 완결 월별 통계는 거부합니다. 오늘 조회한 수정치를 최초 발표일과 결합하면 미래 정보가 섞이므로 그렇게 사용하면 안 됩니다. `vintage`는 설명용이며, 실제 선택은 `released_at`으로 합니다.

발표 이력이 없는 기존 `month,value` CSV와 KOSIS API는 **월+2 첫날** 가정을 유지합니다(7월 → 9월 1일). 실제 발표일 복원이 아니며, 과거 수정치·발표 지연으로 인한 누출 가능성이 남습니다. `config.json`의 `macro_info.availability_modes`에서 `supplied_release_history`와 `lagged_latest_vintage`를 구분합니다. 발표 시각을 제공했다는 것만으로 이력의 완전성이 입증되는 것은 아닙니다. 자료는 100일 뒤 만료되며, 과거 월의 수정만으로 오래된 최신 관측의 유효기간을 연장하지 않습니다.

**추가 월별 지표:** 기본 두 지표를 정상적으로 불러온 뒤, 같은 `macro_inputs/` 폴더에 다음 파일이 있으면 읽습니다. `month,value` 및 선택적 `released_at,vintage,source` 형식을 사용합니다.

| 파일 | 준비할 공식 자료 | 특징 |
| --- | --- | --- |
| `daily_exports.csv` | 산업통상부·관세청의 **조업일수 기준 한국 전체 일평균 수출**, 달러/조업일 | 로그, 전년·전월 증가율, 3개월 평균, 증가율의 1·3개월 변화 |
| `oecd_g20_cli.csv` | [OECD CLI](https://www.oecd.org/en/data/datasets/oecd-composite-leading-indicators-clis.html)의 **Major G20, amplitude adjusted**, 장기평균=100 | 100 대비 수준, 1·3개월 변화 |

일평균 수출의 분모는 달력 일수나 KRX 거래일 수가 아닙니다. 총수출과 조업일수가 같은 발표·집계 범위에 속하는지 확인하세요. ICT 반도체와 월별 수출입동향의 반도체 분류를 확인 없이 연결하거나 서로 빼지 않습니다. 두 추가 지표의 자동 다운로드는 연결하지 않았습니다. OECD 공개 API는 개발 환경에서 HTTP 403으로 실제 응답을 검증하지 못했습니다. 공식 자료를 위 형식으로 준비해야 하며, 누락·형식 오류·짧은 이력·최신 결측은 화면과 `optional_status`에 기록하고 해당 추가 지표만 제외합니다.

추가 효과는 동일한 평가 날짜·학습 구간·내부 모델 선택 방법으로 `Mean ensemble`과 `No macro ensemble`을 비교합니다. `macro_comparison.csv`에 정확도·균형 정확도·log loss 차이와 신뢰구간을 저장하며, 앞으로 두 모델의 사전 예측도 함께 원장에 쌓습니다. 상관관계가 있어도 다음 거래일 방향의 정확도가 반드시 높아지는 것은 아닙니다.

**20거래일 가격 예측도 비교합니다.** `price_macro_comparison.csv`에 거시지표 포함/미포함 Ridge의 쌍체 MAE 차이와 월 블록 95% 신뢰구간을 저장합니다. 동일한 날짜·시간순 분할·변동성 모형을 사용하며, 각 모델의 보정·신호 선택·최종 평가는 분리합니다. `raw_*`는 축소 전 모델, `center_*`는 신호 선택까지 거친 중심값의 오차입니다. 단위는 수익률(0.01=1%p)이고 차이는 **거시 포함−시세만 사용**이므로 음수가 유리합니다. 두 모델 모두 신호를 통과하지 못하면 중심값 차이는 0일 수 있습니다. 날짜별 예측은 `price_macro_oof_20d.csv`에 저장되며 `is_evaluation=True`인 행만 최종 평가입니다. 이 평가 결과로 발행 모델을 자동 교체하지 않습니다.

로컬 저장 폴더의 `macro_snapshots/<해시>.csv`와 JSON은 내려받은 수치와 최초 관측 시각을 보존합니다. 통계가 수정되면 새 스냅샷을 만듭니다. 실행별 `macro_monthly.csv`, `macro_daily_features.csv`, `config.json`과 예측 원장의 `macro_snapshot_hash`로 당시 입력을 추적할 수 있습니다. 이 스냅샷은 수집 시작 전의 발표 이력을 복원하지 않습니다. `USE_DATA_CACHE=True`는 시세·월별 지표 모두 저장 자료 재현용이며 매일 갱신할 때는 `False`를 유지하세요.

## 비교 모델

### 다음 거래일 방향 예측

1. 항상 보합을 예측하는 기준선 (학습 구간의 클래스 사전확률)
2. 다항 로지스틱 회귀 — 과거 내부 3개 시계열 구간에서 `C`와 클래스 가중치를 선택
3. LightGBM 분류기 — 과거 내부 검증에서 60/120트리와 클래스 가중치를 선택(7리프)
4. 30거래일 특징 시퀀스를 사용하는 소형 Transformer Encoder — `RUN_TRANSFORMER`, 기본 꺼짐(실험용, 앙상블 미포함)
5. 금융 OHLCV 시계열 파운데이션 모델 [Kronos-small](https://github.com/shiyu-coder/Kronos)의 zero-shot 예측 — `RUN_KRONOS`, **기본 꺼짐**
6. `ENSEMBLE_MODELS`의 확률을 **단순 평균**한 앙상블

모델은 `accuracy`, `balanced_accuracy`, `macro_f1`, `log_loss`, `Brier score`에 **신뢰구간을 붙여** 비교하고, 여기에 갭/세션 분해와 "항상 보합" 대비 쌍체 차이를 함께 보고합니다.

### 시초가예측과 1거래일·1주일·1개월 종가예측

변동성 스케일 타깃에 Ridge를 적용합니다. OOF(과거 데이터로 학습한 모델의 후속 구간 예측)를 시간순으로 보정 50%, 신호 선택 25%, 최종 평가 25%로 나눕니다. 경계에서는 예측 기간만큼 겹치는 라벨을 제거합니다.

축소계수와 구간 폭은 보정 구간에서 정하고, 신호 선택 구간에서 0% 기준선 대비 손실 차이의 신뢰구간이 음수일 때만 점 예측을 제공합니다. 마지막 평가 구간의 실제값은 이 선택에 사용하지 않습니다. `band_coverage`는 최종 평가 구간에서 측정한 적중률이므로 명목 80%와 다를 수 있습니다.

신호가 없으면 `predicted_close`와 `predicted_return`은 비워 둡니다. `center_close`는 현재 종가를 기준으로 제공하며, 이후 실제 종가와의 차이는 `center_price_error`에 따로 저장합니다.

### 개선 여부 확인

분류 모델은 각 외부 폴드의 과거 데이터 안에서만 설정을 고릅니다. 내부 검증 정확도를 우선하고 동률이면 log loss를 비교합니다. 온도 보정은 확률의 크기를 조절하되 예측 클래스는 바꾸지 않습니다. 최신 예측도 백테스트와 동일하게 최근 5년으로 학습합니다.

`Previous ensemble`은 이전 고정설정(Logistic C=0.01, LightGBM 60×7, 두 모델 모두 balanced 가중치)의 평균입니다. `improvement_vs_previous.csv`에 새 앙상블과 이 기준선의 정확도·balanced accuracy·log loss 차이 및 쌍체 월 블록 신뢰구간을 저장합니다. 정확도 향상은 보장하지 않으며, 외부 평가 차이의 신뢰구간이 0을 포함하면 개선이 확인되지 않은 것으로 읽습니다.

## 데이터 무결성 장치

노트북은 실행할 때마다 다음을 검사하고, 문제가 있으면 **조용히 넘어가지 않고 출력하거나 중단**합니다.

- **자산별 신선도·공백 검증** — 마지막 봉이 7일 이상 뒤처졌거나 최근 250거래일 중 5일 넘게 빠진 보조 자산은 경고와 함께 제외합니다.
- **구멍 차단** — 한국 지수는 삼성 거래일 달력에 먼저 맞춘 뒤 차분하고, `safe_pct_change`가 시계열 구멍을 NaN으로 만들어 다기간 이동이 1일 수익률로 둔갑하는 것을 막습니다.
- **학습 구간 지연 검사** — `dropna` 이후 학습 데이터가 최신 봉보다 10일 넘게 뒤처지면 원인 컬럼을 출력하고 `assert`로 중단합니다.
- **미완성 봉 제거** — 자산군별 마감 시각(한국 15:40, 미국 16:05, 런던 16:35, FX·선물 17:05)을 기준으로 아직 마감되지 않은 당일 봉을 버립니다. 이전에는 실행 시각에 따라 라이브 확률이 달라졌습니다.
- **유령봉 제거** — 거래량 0에 시가=고가=저가=종가인 Yahoo 유령봉은 `target_return`을 정확히 0으로 만들어 "보합" 라벨을 조작하므로 삼성전자에서 제거합니다.
- **라이브 행 점검** — 과거값으로 대체된 특징과 그 출처 날짜를 출력하고, 학습 분포의 0.1~99.9% 범위를 벗어난 값을 경고합니다.

## 데이터 누수 방지와 검증 방식

- 예측 대상 날짜를 `d`라고 할 때 삼성전자와 한국 시장 특징은 `d-1` 거래일까지의 정보만 사용합니다.
- 미국 시장 종가는 한국 시간으로 다음 날 새벽에 확정된다고 보고, 가용 날짜를 하루 뒤로 이동해 결합합니다.
- 데이터를 무작위로 섞지 않고 최근 5년을 학습한 뒤 다음 6개월을 평가합니다.
- Transformer의 scaler와 모델은 각 폴드의 과거 데이터만 사용해 다시 학습합니다. 조기종료로 최적 epoch를 정한 뒤 **학습 구간 전체로 다시 적합**합니다(이전에는 최근 15%가 학습에 들어가지 않았습니다).
- 중기 가격 예측은 학습 라벨과 검증 구간이 겹치지 않도록 예측 기간에 맞춘 `gap`을 둡니다.

이 방식은 명백한 미래 정보 유입을 막기 위한 장치이지만, 실거래 환경의 거래비용, 체결 가능성, 데이터 발표 지연까지 완전히 모사하지는 않습니다.

[+0.0044, +0.0141] → 편입 반대**. 확률 품질은 "항상 보합"과 동률이고 앙상블을 유의하게
해친다. 그래서 `RUN_TRANSFORMER` 기본값을 다시 껐다. 다시 재려면 True로 두고 실행하거나
Actions의 "Transformer 실험" 워크플로를 돌리면 같은 기록이 쌓인다.

편입은 자동으로 하지 않는다. `summary.csv`에 같은 판정이 여러 실행에서 반복되면 그때
`ENSEMBLE_MODELS`에 `"Transformer"`를 추가할지 정한다. 단, Actions에는 GPU가 없으므로 편입하면
매일 발행을 어떻게 돌릴지(가중치 저장 후 추론만, 또는 CPU 학습 시간 측정)를 먼저 정해야 한다.

동작 방식과 주의사항입니다.

- 예측은 **불변**입니다. 같은 `record_id`는 다시 올려도 최초 예측을 유지하고, 실제값·오차만 갱신됩니다. 여러 기기에서 실행해도 `record_id` 기준으로 합쳐집니다.

- 오류 메시지에는 토큰이 포함되지 않습니다(HTTP 상태 코드만 표시).
- **저장소가 공개면 예측 원장도 공개됩니다.** 예측값과 실제 종가만 들어 있어 민감 정보는 없지만, 공개를 원치 않으면 저장소를 비공개로 바꾸거나 `SYNC_LEDGER_TO_GITHUB=False`로 두세요.
| `runs/<run_id>/` | 실행별 백테스트, 최신 예측, 학습 설정, 모델 파일 |
| `latest_outputs.zip` | 가장 최근 실행 결과와 누적 CSV 사본 |

`actual_close`는 실제 종가, `actual_return`은 해당 예측 타깃의 실제 수익률, `direction_correct`는 방향 적중(1/0)입니다. `price_error`는 **예상 종가 - 실제 종가**, `absolute_price_error`는 절대 오차(원), `price_ape`는 절대 오차율(비율), `return_error`는 예측 수익률 - 실제 수익률입니다. `interval_hit`는 실제 종가가 예측 구간 안이면 1입니다. 방향 분류에는 예상 종가가 없으므로 가격 오차는 Ridge 가격 예측 행에서 확인합니다.

미래 예측은 `status=pending`으로 유지합니다. `scored`는 실제값 대조 완료, `missing_actual`/`missing_reference`는 필요한 확정 가격을 아직 얻지 못했다는 뜻입니다. 예측 원문은 변경하지 않고 실제값·오차만 새 시세에 맞춰 갱신합니다.

같은 날 여러 번 학습하면 모든 실행을 보존하고, 저장 셀만 다시 실행하면 중복 추가하지 않습니다. 일별 성능은 `close_to_close`에서 09시 이전, `open_to_close`에서 시가 확인 직후 09:05 이전에 생성한 최초 기록만 집계합니다. 나중에 만든 기록은 원장에 남지만 사전 예측 성능에서 제외합니다. 생성 시각을 모르는 기존 형식의 로그도 보존하되 사전 예측 통계에서는 제외합니다.

**Colab 로컬 저장은 런타임 간 자동 보존되지 않습니다.** 다음 실행에서 기록을 이어 쓰려면 다운로드한 ZIP에서 `forecast_log.csv`를 꺼내 `/content/samsung_direction_outputs/forecast_log.csv`로 업로드하세요. 일별 비교와 요약 CSV는 해당 원장으로 다시 계산합니다. KOSIS CSV를 사용한다면 `macro_inputs/`에도 두 파일을 다시 업로드해야 합니다. 동시에 여러 실행이 같은 원장을 쓰는 방식은 지원하지 않습니다.

**이 기능은 노트북 실행 시 저장·채점하는 기능입니다. Colab이 닫힌 상태에서 매일 스스로 실행되는 예약 작업은 아닙니다.** 하루 실행을 건너뛰면 그날의 사전 예측은 만들 수 없지만, 이미 저장한 예측의 실제값은 다음 실행 때 갱신됩니다.

## 결과 해석 체크리스트

1. 갭/세션 분해 표의 `auc_session`이 0.5보다 의미 있게 큰가? `session_bp_net`이 0보다 큰가?
2. `balanced_accuracy`의 신뢰구간이 "항상 보합"의 값을 배제하는가?
3. 쌍체 비교표에서 **CI가 0을 포함하는 차이는 전부 "동률"** 이다.
4. `folds_worse_than_prior`가 절반 이상이면 그 모델은 확률 모델로서 클래스 빈도보다 못하다.
5. 종가예측의 `signal`이 "없음"이면 예상 종가는 현재가와 같다는 뜻이다.
6. 라이브 예측에 "과거값으로 대체된 특징" 경고가 떴다면 그 예측은 신뢰하지 말고 데이터부터 고쳐라.

`tools/build_metals_report.py`가 COMEX 금·은 선물(`GC=F`, `SI=F`)에 대해 삼성전자·SK하이닉스와

**왜 노트북에 종목을 추가하지 않았나.** 노트북 파이프라인은 KOSPI·반도체 피처, 한국 거래일

AUC는 0.52~0.53이다. 보고서는 이 수치를 그대로 보여 주고 "확률은 참고만"이라고 적는다.
쓸모가 있는 쪽은 변동성 구간(목표 80%, 실제 75~81%)이다.

**시각.** 미국 선물 전자세션이 17:00 ET에 끝나므로 그 전이면 당일 봉을 미완성으로 보고 뺀다.

**왜 구글 트렌드가 아닌가.** Trends의 관심도 시계열에는 공식 API가 없고, 값이 조회
구간 안의 상대값(0~100)이라 매일 뽑아 이어 붙이면 서로 다른 척도를 한 줄에 놓게 된다.

**두 지표를 나란히 본다.** 위키백과 조회수(한국어·영어)와 구글 트렌드 검색 지수(KR)를
같은 줄에 놓는다. 구글 트렌드는 공식 API가 없어 웹 UI의 내부 엔드포인트를 쓰므로 언제든
막힐 수 있다 — 실패하면 그 열만 비우고 보고서는 그대로 낸다(`--no-trends`로 끌 수도 있다).
`tools/probe_google_trends.py`가 접근 가능 여부만 확인하는 진단 도구다.

트렌드 값은 조회 묶음 안에서만 정규화된 0~100 상대값이라, 5개씩 나눠 받으면 묶음이 다른
키워드끼리 비교할 수 없다. 모든 묶음에 공통 앵커(`반도체`)를 넣고 앵커 평균의 비율로 척도를
맞춘다. 값이 정수로 반올림되어 오므로 10년 전 지수가 1~2였던 항목은 증가율을 내지 않는다.

**증가율 계산.** 전체 구간에 로그-선형 추세선을 맞춘 연평균값이다. 양 끝 12개월 평균만
비교하는 방식은 쓰지 않는다 — 마지막 한 해의 급등을 10년 추세로 둔갑시키기 때문이다.
실제로 SK하이닉스 검색 지수는 10년간 1~2로 평평하다가 마지막 해에만 33으로 튀었는데,
양끝 방식은 +39%/년, 추세선은 +9.6%/년을 준다. 추세선보다 최근 12개월이 두 배 이상 높은
항목에는 '최근 급등'을 표시한다.
지표가 온전히 덮어야 하는 시작 월(위키 2015-07, 트렌드는 조회 창 첫 달)부터 데이터가 있는
항목에 대해서만 증가율을 낸다. 문서마다 개설 시점이 다른데 자기
자신의 첫 12개월을 기준으로 삼으면, 개설 직후의 낮은 조회수가 분모가 되어 증가율이
폭발하고(챗GPT 한국어 문서는 +820%/년이 나왔다) 무엇보다 구간이 다른 값끼리 순위를
매기게 된다. 개설이 늦은 문서는 사유를 적어 목록 뒤로 보낸다.

추적 대상은 `TOPICS`에 있다. 문서 제목은 리다이렉트를 따라 확인한 정규 제목이어야 한다
(리다이렉트 제목으로 조회하면 그 자체의 낮은 조회수만 돌아온다).

### 환경 차이 추적

Colab과 Actions는 라이브러리 버전이 다르다(Actions는 `requirements.txt` 고정 버전,
Colab은 런타임 기본값). 같은 코드·같은 시드라도 폴드별 지표가 움직이므로, 두 곳에서
발행하면 서로 다른 수치 환경의 예측이 한 원장에 쌓인다.

`config_hash`는 '무엇을 선택했는가'(특징 목록, 밴드, 시드, 지표 포함 여부)만 담아
환경 차이를 구분하지 못한다. 그래서 원장에 두 열을 따로 둔다.

| 열 | 값 |
| --- | --- |
| `runtime` | `colab` / `github-actions` / `local` (`PREDICT_STOCK_RUNTIME`으로 덮어쓸 수 있다) |
| `versions_hash` | `VERSIONS`의 해시. 라이브러리가 바뀌면 값이 바뀐다 |

정확도 집계(`summarize_daily`)는 여전히 `config_hash`로 그룹을 나눈다. 환경이 바뀌었다고
"설정이 바뀌었다"고 기록하면 의미가 흐려지기 때문이다. 두 열은 결과가 갈렸을 때
원인을 되짚기 위한 것이다.

### 발행 주체

**발행은 GitHub Actions에서만 한다.** Colab과 로컬 실행은 결과를 런타임 로컬에만 남기고
저장소에는 올리지 않는다. 양쪽에서 올리면 라이브러리 버전이 다른 예측이 한 원장에 쌓여
정확도 이력의 계보가 섞이기 때문이다.

| `PREDICT_STOCK_PUBLISH` | 결과 |
| --- | --- |
| (없음) | `github-actions`에서만 발행. Colab·로컬은 발행하지 않음 |
| `true` | 어디서든 발행. Colab에서 그때만 올리고 싶을 때 |
| `false` | 어디서든 발행하지 않음 |

발행을 건너뛰면 그 사유가 화면과 마지막 '종목별 발행 결과'에 함께 남는다
(발행 스위치 / `GITHUB_TOKEN` 없음 / 원장 조회 실패).

### 월별 지표가 없을 때

`KOSIS_API_KEY`가 없으면 기본값(`MACRO_STRICT=False`)에서는 경고만 남기고 시세 모델로
계속 진행한다. 이때 `config_hash`가 달라지므로 정확도 집계에서 별개 계보로 채점된다 —
섞이지는 않지만 이력이 두 갈래로 쪼개져 표본이 줄어든다.

**자동 실행에서는 `PREDICT_STOCK_MACRO_STRICT=true`로 즉시 중단시킨다.** 사람이 출력을
지켜보지 않으므로, 지표가 빠진 채 조용히 발행되느니 실패해서 메일을 받는 편이 낫다.
Colab은 지금까지처럼 계속 진행한다.

### 알아둘 점

- **Yahoo Finance가 클라우드 IP를 막을 수 있다.** GitHub 러너 IP는 스로틀·차단
  대상이 되는 일이 있다. 이 경우 자동 실행은 쓸 수 없고, 맥에서 launchd로
  돌리는 쪽으로 바꿔야 한다.
- **결과가 Colab과 정확히 같지 않을 수 있다.** Actions는 `requirements.txt`의
  고정 버전을 쓰고 Colab은 런타임 기본 버전을 쓴다. 실제 사용 버전은 매 실행마다
  원장과 보고서에 기록되므로 추적은 된다.
- **cron은 정시를 보장하지 않는다.** 수십 분 밀리는 일이 잦다. 07:00 KST로 잡은 것은
  모델이 07:00 시점 예측이고, 미국 장 마감(겨울 06:00 KST)이 야후 일봉에 반영될
  여유가 필요해서다. 밀려도 장 시작(09:00 KST) 전에는 끝난다.
- **Pages 재빌드를 명시적으로 요청한다.** 보고서는 git push가 아니라 Contents
  API로 커밋되는데, `GITHUB_TOKEN`이 만든 커밋은 다른 워크플로를 트리거하지
  않으므로 Pages 빌드가 자동으로 돌지 않을 수 있다.
- **실패하면 GitHub이 저장소 소유자에게 메일을 보낸다.** 예약 실행이 실패했을 때
  알림을 받는 기본 경로다.
