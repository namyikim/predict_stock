# 카카오톡 본인 알림 연결 준비

2026-10-07 공식 문서 확인. **K2 운영 연결·인증 확인 완료 / K3 발송 구현 / 추가 D1·Worker 배포와 실제 수신 확인 대기**.
기존 계획: [이메일 유입·카카오톡 연결](email-traffic-tracking-plan.md).

## 이번에 선택한 범위

보고서가 게시되면 운영자 본인의 카카오톡 ‘나와의 채팅’으로 회차 요약과 링크를 보낸다.
기존 이메일 수신자에게 카카오톡을 일괄 발송하거나 친구 목록을 수집하지 않는다.

| 방식 | 용도와 제약 | 이번 적용 |
| --- | --- | --- |
| 나에게 메시지 REST API | 로그인·talk_message 동의한 본인에게 발송 | 우선 구현 대상으로 선정 |
| 카카오톡 공유 | 이용자가 버튼을 눌러 대화방을 선택; 서버 예약 발송 기능이 아님 | 별도 기능 |
| 친구에게 메시지 API | 같은 서비스 이용자 간 상호작용; 친구/메시지 추가 권한 심사 등 필요 | 제외 |
| 비즈니스 알림톡 | 서비스→고객 알림 용도; 비즈니스 채널·템플릿 심사·공급사 계약/요금 확인 필요 | 구독자 전체 발송 요청 때 별도 검토 |

메시지 API의 공개 일간 쿼터는 앱 30,000건, 발신자/수신자 각 100건, 발신자-수신자 쌍 20건이다.
앱 실제 쿼터·정책은 개발자 콘솔에서 다시 확인한다. 우선 개장 전/마감 후 통합 알림 각 한 건으로
설계하고 유료 API 설정은 켜지 않는다. 알림톡의 계약별 가격은 이번에 확인하지 않았다.

## 사용자가 먼저 준비할 것

1. [카카오디벨로퍼스](https://developers.kakao.com/)에서 본인 카카오계정으로 로그인하고 앱을 만든다.
   이미 사용할 앱이 있으면 새로 만들 필요 없다. 개발자 등록·약관 동의는 본인이 수행한다.
2. 해당 앱의 **카카오 로그인**을 활성화한다.
3. **카카오 로그인 → 동의항목 → 접근권한 → 카카오톡 메시지 전송**을 설정한다.
   권한 이름은 `talk_message`. 목적은 ‘본인이 요청한 예측 보고서 요약과 링크를 나와의 채팅에 전달’이다.
4. **앱 → 제품 링크 관리 → 웹 도메인**에 `https://namyikim.github.io`를 등록한다.
   메시지 링크는 `/predict_stock/` 하위 보고서로 제한한다.
5. 앱 준비 여부만 알려준다. REST API 키, Client Secret, 인가 코드, 액세스/리프레시 토큰을
   대화·Git·화면 캡처에 붙이지 않는다. 키 설정과 로그인 연결은 인증 코드가 준비된 다음에 안내한다.

**최초 로그인은 아래 K2 배포 순서대로 Worker와 D1을 적용하고 리다이렉트 URI를 등록한 뒤 진행한다.**
시험 메시지는 K3 배포 후 관리자 화면에서 내용·본인 수신을 확인하고 보낸다. 임시 토큰을 영구 자동 발송 설정으로 사용하지 않는다.

## 인증·발송 설계

### 인증과 비밀값

- 현재 단일 파일 Worker 수동 배포 방식을 유지한다. REST API 키·Client Secret·토큰 암호화 키는
  Cloudflare Secrets에 보관한다. 카카오 인가·토큰 요청은 공식 엔드포인트만 사용한다.
- 관리자 인증을 거친 연결 시작에서 일회용 state를 발급하고, 짧은 만료·브라우저 세션 결합·재사용 거부를 적용한다.
  STATS_TOKEN은 URL/인가 state에 넣지 않는다. 콜백에서 state·앱·연결 대상 확인을 마친 뒤 토큰을 저장한다.
- 액세스/리프레시 토큰은 서버 저장소에 암호화해 보관한다. 갱신 응답에 새 refresh_token이 없으면
  기존 값을 유지하고, 있으면 교체한다. 동시 갱신을 제어하며 만료/동의 철회 시 재연결 상태를 표시한다.
- 관리자 응답·예외 로그에는 토큰과 인가 코드 원문을 내보내지 않는다. 연결 해제는 전송 중지와
  서버 토큰 폐기를 수행하며 카카오 연결 해제 API의 영향도 따로 안내한다.

### 발송과 중복 방지

- 게시 검증을 마친 기존 mail_events의 보고서 내용을 읽되, 이메일 발송 성공이나 구독자 존재를
  카카오 발송 조건으로 삼지 않는다. 별도 카카오 제어·발송 원장을 둔다.
- 앱/본인 계정/회차일/개장 전·마감 후별 유일 키로 한 회차를 한 번만 접수한다. 토큰 갱신이나 재연결도 같은 회차를 다시 만들지 않는다. 이메일 일시 중지와
  카카오 일시 중지는 구분하고, 카카오 기본값은 꺼짐이다.
- 기본 텍스트 템플릿과 `POST https://kapi.kakao.com/v2/api/talk/memo/default/send`를 사용한다.
  날짜·회차·삼성전자/SK하이닉스의 실제 보고서 요약·전체 보고서 링크를 포함한다.
- 길이 제한과 허용 링크를 검사한다. 성공 응답 `result_code=0`은 API 전송 성공으로 기록하며
  수신자의 열람으로 표시하지 않는다. 재시도 중복 방지 기능이 있다고 가정하지 않는다.
- 시간 초과 등 실제 전송 여부가 불명확하면 자동 재발송하지 않고 확인 필요로 표시한다.
  인증 갱신·권한 부족·쿼터·확정 거절은 구분하고 카카오 실패가 이메일을 막지 않도록 분리한다.

### 관리자와 방문 집계

- 연결/만료/재연결 필요, 최근 시도·전송 성공·실패·확인 필요, 중지/재개 표시.
- 카카오 유입은 `utm_source=kakao`로 이메일과 분리한다. 수신자 식별값 없이 보고서/회차만 전달한다.
  기존 이메일 파서·통계 호환을 유지하며 카카오 내부 브라우저의 표시도 검증한다.

## K2 적용 순서 — 2026-10-07

GitHub Actions에 등록한 `KAKAO_KEY`는 그대로 둔다. 이번 인증 서버는 Cloudflare Worker이므로
같은 REST API 키를 Worker Secret에도 설정해야 한다. GitHub Secret 값을 Worker가 자동으로
읽거나 복사하지 않는다. 발송 코드는 K3에서 연결하며 현재는 로그인해도 메시지를 보내지 않는다.

| Worker 설정 이름 | 종류 | 설정 내용 |
| --- | --- | --- |
| `KAKAO_KEY` | Secret | 등록한 앱의 REST API 키. `KAKAO_REST_API_KEY`도 지원하지만 두 이름의 값이 다르면 연결을 막는다. |
| `KAKAO_CLIENT_SECRET` | Secret | 카카오 로그인 Client Secret. 앱에서 활성화돼 있으면 반드시 설정한다. |
| `KAKAO_TOKEN_KEY` | Secret | AES-GCM용 무작위 32바이트의 Base64 값. 아래 명령을 본인 컴퓨터에서 실행해 생성한다. |
| `KAKAO_APP_ID` | 일반 변수 | 카카오 개발자 콘솔의 숫자 앱 ID. REST API 키와 다른 값이다. |
| `KAKAO_PUBLIC_URL` | 일반 변수 | `https://predict-stock-counter.kimname1.workers.dev` |

암호화 키 생성 명령(출력은 Worker Secret에만 넣는다):

```sh
python -c 'import secrets,base64; print(base64.b64encode(secrets.token_bytes(32)).decode())'
```

1. D1에 [`counter/migrations/20261007_kakao_auth.sql`](../counter/migrations/20261007_kakao_auth.sql)의
   문장을 하나씩 적용한다. 새 표 두 개와 인덱스만 추가하며 기존 방문·이메일 표는 바꾸지 않는다.
   `CREATE ... IF NOT EXISTS`이므로 반복 적용할 수 있다.
2. Worker의 위 설정을 추가하고 `counter/worker.js` **전체** 코드를 Deploy한다. 사이트 push만으로
   Worker가 자동 배포되지 않는다.
3. 카카오 로그인 Redirect URI에 정확히 아래 주소를 등록한다.
   `https://predict-stock-counter.kimname1.workers.dev/kakao/callback`
4. 관리자 → **카카오톡 연결**에서 STATS_TOKEN 입력 → 연결 상태 확인 → 카카오 로그인 연결을 누른다.
   본인 카카오계정으로 로그인하고 `talk_message`에 동의한다. 관리자 토큰은 인가 URL에 들어가지 않는다.
5. 관리자 화면으로 돌아온 뒤 **연결 상태 확인** → 표시된 회원번호가 방금 로그인한 본인 계정인지
   확인 → **본인 계정 확인**을 누른다. 인증 대기는 연결 시작부터 10분 안에 끝내야 한다.
6. **인증 갱신 확인**은 유효 토큰을 확인하거나 만료 임박 시 갱신한다. 메시지 전송 시험이 아니다.
   자동 알림은 계속 꺼져 있다. K3 발송 원장·게시 이벤트 연결과 K4 상태·유입 집계가 후속이다.

- 사용자는 D1 새 표 두 개·인덱스, Worker 설정·전체 코드 배포, 카카오 로그인 ON·리다이렉트 URI·
  `talk_message` 선택 동의를 완료했다고 보고했다. 운영 설정값은 독립 확인하지 않았다.
- `KOE101` 발생 후 REST API 키를 다시 등록하자 동의 화면까지 진행됐다. 13:03 KST 기준 관리자에는
  `미연결 · 카카오 인증 응답을 받지 못했습니다`가 반복돼 본인 계정 확인은 아직 완료되지 않았다.
- 이 문구는 외부 호출 준비·통신·시간 초과·JSON 해석 예외를 함께 표시한다. 13:03 KST에는 원인이 미확정이었다.
  `kakaoCall`에 `[kakao-auth]` 진단 로그를 추가해 API 종류, 실패 단계, HTTP 상태, 허용된 예외 이름,
  JSON 여부, 시간 초과 API 지원 여부만 기록한다. 요청 URL·헤더·본문·외부 응답 원문·예외 메시지는 기록하지 않는다.
- 진단 코드는 Worker 전체 파일을 다시 Deploy해야 적용된다. Cloudflare 로그를 수집하는 상태에서 새 로그인 후
  `Observability`의 `[kakao-auth]` 로그 내용만 확인한다. 콜백 URL의 인가 코드나 토큰이 포함된 이벤트 원문은 공유하지 않는다.
- 모의 외부 응답으로 통신 예외·시간 초과·비 JSON 응답·런타임 API 부재와 로그 비밀값 미노출을 검증했다.
  이 모의 검증만으로 운영 장애 해결을 판단하거나 자동 발송을 켜지 않는다.

13:09 KST에 사용자가 제공한 진단 로그는 `api=token`, `stage=request`, `http_status=0`,
`error_name=TypeError`, `timeout_supported=true`였다. Cloudflare workerd의
[`Request` 구현](https://github.com/cloudflare/workerd/blob/main/src/workerd/api/http.c%2B%2B)은
`redirect:'error'`를 거부한다. 실제 workerd 2026-10-07에서 기존 `kakaoCall`을 실행해 같은 실패를
재현한 뒤 `redirect:'manual'`로 수정하고 3xx 응답을 JSON 해석 전에 직접 거절했다.
실제 런타임의 정상 토큰 요청과 301/302/303/307/308 거절 검사가 통과했다. 관련 회귀 검사 34개도
통과했다. 런타임 검사는 `WORKERD_BIN` 또는 PATH의 `workerd`가 있을 때 실행하며 없으면 건너뛴다.
외부 카카오 호출·운영 토큰 교환은 로컬 검증에 포함하지 않았다.

  이는 사용자에 의한 실제 연결·인증 확인 기록이다. 액세스 토큰 만료에 따른 실제 갱신 교환은
  독립 확인하지 않았다. 회원번호와 비밀값은 이 기록에 적지 않는다.
- K2 운영 연결 확인을 완료했다. 자동 보고서 발송과 실제 카카오톡 수신은 K3 후속이며 아직 꺼져 있다.

### 동작과 보관 범위

- Pages에서 Worker로 직접 이동한 뒤 쿠키를 발급하므로 제3자 쿠키 허용에 의존하지 않는다.
  일회용 연결 코드·state의 해시와 `HttpOnly; Secure; SameSite=Lax` 쿠키를 함께 확인한다.
  만료·재사용·중복 파라미터·앱 설정 변경은 카카오 토큰 요청 전에 거절한다.
- 카카오 토큰 정보의 앱 ID와 회원번호, 실제 `talk_message` 동의를 확인한다. 최초 로그인은
  암호화된 대기 상태로 두고 관리자 확인 뒤 계정을 고정한다. 다음 로그인에서 다른 계정으로
  조용히 바꾸지 않는다. 이름·이메일·친구 목록은 요청하거나 저장하지 않는다.
- 액세스/갱신 토큰은 무작위 IV를 사용하는 AES-256-GCM으로 암호화하고 앱 ID·회원번호와 결합한다.
  D1에는 암호문과 만료 시각, 연결 회원번호, 상태만 둔다. 관리자 API·로그에는 토큰·인가 코드·
  카카오 오류 응답 원문을 반환하지 않는다. 인증 대기 행은 만료 후 다음 Cron 또는 연결 시작에서 지운다.
- D1의 조건부 갱신 임대로 동시에 한 번만 토큰을 갱신한다. 새 갱신 토큰이 빠지면 기존 토큰과
  만료를 유지한다. 토큰이 교체되면 권한 조회 전에 암호화해 보존해 일시 장애로 새 토큰을 잃지 않는다.
  권한 재확인 대기 중에는 토큰을 발송 코드에 넘기지 않으며 다음 시도에서 다시 확인한다.
- **연결 해제**는 자동 전송 중지와 서버 토큰 폐기를 수행한다. 진행 중인 인증/갱신은 버전 검사로
  연결을 복원할 수 없다. 확인한 회원번호는 같은 본인 계정 재연결을 위해 유지한다.
- ‘카카오 앱 동의도 해제’를 체크한 경우에만 공식 연결 해제 API를 추가로 호출한다. 같은 앱의
  다른 로그인 기능에도 영향을 줄 수 있다. API 실패·토큰 만료·암호키 손실 시 로컬 토큰은 먼저
  지우고 카카오계정의 연결된 서비스에서 수동 해제가 필요하다고 표시한다. 원격 해제 진행 중에는
  재연결·중복 해제를 차단한다. 원격 결과를 확인하지 못하면 재연결을 계속 차단하며, 계정에서
  앱 동의가 해제된 것을 직접 확인한 뒤 **앱 동의 해제 결과 확인**으로 차단을 해제한다.
- 암호화 키를 바꾸거나 잃으면 기존 토큰을 읽을 수 없다. 서버 연결을 해제하고 새 키로 다시
  로그인해야 한다. 이 버전은 암호화 키의 자동 이전을 지원하지 않는다.

### 구현 검증 기록

- 테스트 먼저 작성해 미구현 경로의 404를 확인한 뒤 실제 Worker·SQLite로 인증 수명주기를 검증했다.
- 관리자 모의 DOM으로 인증 헤더·로그인 이동·계정 확인·해제·이행 미적용·권한 오류 표시를 검증했다.
- 카카오 API는 모의 응답만 사용했다. 실제 로그인·카카오 메시지·운영 D1 변경·Worker Deploy는 하지 않았다.
- 인증/관리자·기존 카운터·메일·이메일 유입·전체 메뉴 링크 회귀 검사 35개 통과. 기존 실험실 48개와 KRX 일정 61개 검사도 통과했다.
- 전체 `python -m unittest discover -s tests`는 1,946개를 실행해 노트북 setup의 `tqdm` 미설치 오류 1건과 Torch 부재로 인한 건너뜀 15개를 확인했다. 다른 실패는 없었다.
  `tqdm`과 추가로 확인한 `Jinja2`를 설치한 뒤 노트북 전 셀 실행·보고서/원장 생성·게시 금지 검사 5개가 통과했다. 환경 보완 후 전체 명령을 다시 실행하지는 않았다.
- 구현 당시 실제 브라우저/모바일·운영 D1·Worker 배포·본인 로그인·수신은 미확인이었다.
  이후 사용자 배포·로그인·인증 확인은 위 운영 연결 진단에 기록했다. 모바일·메시지 수신은 아직 미확인이다.
  사용자가 커밋·main push를 승인했다.


최종 리뷰에서 원격 앱 동의 해제와 재연결의 경합을 재현했다. 해제 진행/결과 미확인 상태와
버전 검사를 추가하고 모의 unlink 대기·타임아웃으로 검증했다. state 소비 직후 다른 탭에서
해제해도 인가 코드 URL에 머물지 않고 관리자 화면으로 복귀한다. 실제 다른 계정의 앱/권한
응답을 일치시킨 테스트로 수신 계정 교체 거절도 확인했다.

후속 K3에서 보완할 경미한 사항: KAPI HTTP 400의 `code=-10` 쿼터 응답은 현재 일반 공급자
오류로 안내한다. HTTP 429는 요청 제한으로 구분하며, 인증 정보 노출이나 자동 발송은 없다.


전체 검사에서 이전 이메일 유입 변경으로 생긴 기존 실험실 테스트 오판을 확인했다. 공개
보고서 셀의 `attribution` 전체 부분문자열을 금지해 `traffic_attribution.js`까지 모델 기여도
분석으로 취급하던 검사였다. 금지 대상인 `live_contributions`와 `attribution.csv`를 확인하도록
범위를 좁혔고 실험실 테스트 48개가 통과했다. 화면과 모델 기여도 기능은 변경하지 않았다.


## K3 발송 적용 순서 — 2026-10-07

구현은 [K3 실행 계획](kakao-k3-implementation-plan.md)을 따른다. 기존 인증 연결과 암호화 키를 유지한 채 아래를 추가 적용한다.

1. Cloudflare D1 Console에서 [`20261007_kakao_delivery.sql`](../counter/migrations/20261007_kakao_delivery.sql)을 **CREATE TABLE 두 문장과 CREATE INDEX 한 문장으로 나누어** 실행한다. 반복 실행 가능하며 기존 인증/이메일 표를 바꾸지 않는다.
2. `counter/worker.js` 전체 코드를 Worker에 붙여 넣고 Deploy한다. 관리자 정적 화면은 GitHub Pages 배포로 반영된다.
3. 카카오 앱 → 플랫폼 설정과 별도로 **앱 → 제품 링크 관리 → 웹 도메인**에 `https://namyikim.github.io`를 등록한다. 로그인 성공만으로 메시지 링크 도메인 등록이 완료되지는 않는다.
4. Worker Cron Triggers에 `*/5 * * * *`가 있는지 확인한다. 있으면 중복 추가하지 않는다. 이 Cron이 새 게시 회차와 확정된 요청 제한의 재시도를 처리한다.
5. 관리자 → 카카오톡 연결 → **발송 상태 확인**을 누른다. **시험 메시지 미리보기**의 본문과 링크를 확인한다.
6. **시험 메시지 보내기**를 눌러 확인 창의 회원번호가 본인인지 확인하고 승인한다. 나와의 채팅에 한 건을 보낸다. 시험은 하루 최대 3건이며 자동 발송을 켜지 않는다.
7. `전송 접수 성공`과 실제 나와의 채팅 수신을 구분해서 확인한다. 수신을 확인한 뒤 **자동 알림 켜기**를 누른다.

### 동작·보관·실패 의미

- 발송은 이메일의 `MAIL_ENABLED`, 일시 중지, 발신자 설정, 구독자 유무에 의존하지 않는다. 기존 게시 검증을 통과해 `mail_events`에 저장된 삼성전자·SK하이닉스 두 보고서를 사용한다.
- **켠 이후 새로 등록된 회차**만 보낸다. 이미 등록된 아침 회차를 오후에 켜도 소급 전송하지 않는다. 개장 전은 한국 시간 09:00 이전, 마감 후는 15:30 이후 당일에만 보낸다.
- 날짜·회차, 두 종목 실제 요약 일부와 두 개의 전체 보고서 버튼을 200자 텍스트 템플릿으로 보낸다. 긴 원문은 말줄임표로 줄인다. 외부 URL·회원 식별값을 링크에 넣지 않는다.
- 전용 `kakao_delivery_settings`는 활성화 시각·설정 세대를, `kakao_deliveries`는 공개 본문·앱/계정 조합의 해시·회차·시각·상태를 보관한다. 발송 기록은 30일 뒤 Cron에서 지운다. 토큰은 기존 인증 표의 암호문으로만 보관한다.
- `sent`: 카카오 API가 `result_code=0`으로 접수했다. 사용자 수신·열람을 뜻하지 않는다.
- `pending`: 인증 선행 확인 또는 HTTP 429/쿼터 코드 -10의 확정 거절 후 재시도 대기. 보고서의 실제 발송 요청은 최대 3회, 확정 요청 제한은 5분 뒤 재시도한다. 시험 메시지는 자동 재시도하지 않는다. 인증 확인 중 막힌 시험 요청은 같은 요청 키를 유지하고, 잠시 뒤 버튼을 다시 눌러 확인한다.
- `uncertain`: 통신 예외·시간 초과·5xx·잘못된 성공 본문·중단된 전송 임대. 중복을 피하기 위해 자동 재전송하지 않는다. 나와의 채팅에서 수신 여부를 확인한다.
- `failed`: 인증/권한·앱/링크 설정 등의 확정 거절. 카카오 일간 한도 코드 -532/-533/-536은 `daily_limit`으로 구분하고 당일 재시도하지 않는다. 관리자 최근 발송 기록을 확인한다. 토큰·응답/예외 원문은 표시하지 않는다.
- 중지·재개는 대기 행을 취소한다. 같은 회차 재생성도 막는다. 이미 전송을 시작한 메시지는 중지·연결 해제로 회수할 수 없다.
- UI의 `utm_source=kakao` 링크는 준비됐으나 채널별 유입 통계는 K4 후속이다. 방문자/수신자의 새로운 개인정보를 수집하지 않는다.

### K3 구현 검증 기록

실제 Worker와 SQLite로 인증·발송·관리자 및 기존 이메일/카운터 관련 36개 검사가 통과했다.
게시 이벤트 HTTP 등록→Cron→카카오 호출을 이메일 꺼짐/구독자 없음에서도 검증했다.
동시 Cron·같은 시험 요청·토큰 갱신 후 같은 회차·중지/해제 경합·불명확 응답·쿼터 재시도·본문 고정·두 종목 대기·200자/링크·D1 반복 이행을 포함한다.
외부 카카오 API는 모의 응답이며 운영 D1 추가 적용·새 Worker 배포·실제 시험 수신·자동 발송 켜기는 사용자 적용 대기다.


독립 코드 리뷰 후 동일 시험 요청을 한국 날짜가 바뀌어도 한 번만 처리하도록 보완했다.
인증 대기 중의 반복 클릭은 같은 시험 요청을 유지하며, 전날 끝내지 못한 요청은 취소 후 새로운 확인을 받는다.
자정 경계·인증 대기 재시도·카카오 일간 한도 분류를 실패하는 검사로 재현한 뒤 수정했고, 최종 관련 36개 검사가 다시 통과했다.

전체 `python -m unittest discover -s tests -v`는 1954개를 실행해 실패 없이 끝났으며 Torch 부재로 15개를 건너뛰었다. 전체 실행 중 진행한 리뷰 수정은 위 최종 관련 36개 재검사로 확인했다. 주간 브리핑 외부 조회 대기도 원래 실행에서 정상 종료됐다.
