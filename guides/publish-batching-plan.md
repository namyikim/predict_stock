# 발행 커밋 묶기 계획 — 실행 한 번 = 커밋 한 번

상태: 계획. 구현 전. 사용자가 토큰 상황을 보며 단계별로 진행한다(2026-09-23).

## 문제

- 하루 커밋 400~630개(2026-09-20~22 실측), 대부분 파일 1개짜리. 전체 이력 9,232개.
- Pages 빌드가 3일간 84회 취소, 9회만 성공 — 커밋마다 빌드가 시작되고 다음 커밋이 앞 빌드를 취소한다. 보고서 반영이 늦어진다.
- push 경합이 잦다(워크플로끼리, 사람 push 와).

원인: `tools/github_pages.publish()` 가 Contents API 로 **파일 하나 = 커밋 하나**를 만든다. 10개 도구가 60여 곳에서 호출하고, 노트북 `github_put()`(8곳)과 `build_trends/ai_news/interest_report.py` 의 `publish()` 사본도 같은 방식이다. 실행 한 번에 파일 5~17개 → 커밋 5~17개.

## 목표

1차 목표는 **도구 하나의 실행 = 변경이 있을 때 커밋 한 번**이다. 기존 호출부는 가능한 한 유지한다. 서로 다른 Python 프로세스가 실행하는 전체 워크플로를 한 커밋으로 묶는 작업은 별도 범위로 둔다.

## 설계

1. **`github_pages.Batch`** — `publish()` 와 같은 인자를 모았다가 `commit()` 때 Git Data API 로 한 번에 올린다.
   - `GET ref` → 파일마다 `POST blobs` → `POST trees`(base_tree = 현재 트리) → `POST commits` → `PATCH ref`.
   - `force:false`로 ref를 갱신한다. 경합이 확인된 경우에만 최신 ref 기준으로 최대 4회 재시도한다. 같은 파일이 바뀌었으면 최신 내용을 다시 읽어 작업을 재적용하거나 안전하게 중단한다. 상세 충돌 정책은 아래 검토 보완 사항을 따른다.
   - 같은 경로를 두 번 넣으면 마지막 것만 쓴다.
2. **점진 이행** — `with github_pages.batch("report: …"):` 블록 안의 `publish(...)` 는 컨텍스트 변수로 배치에 들어가고, 블록 밖 호출은 **지금처럼 즉시 커밋**한다. 한 번에 다 바꾸지 않아도 된다.
3. **예외 시 커밋하지 않는다** — 블록을 예외로 빠져나가면 아무것도 올리지 않는다. 반쯤 만든 보고서가 올라가지 않고, "실패하면 지난 조각 유지" 원칙과 같다.
4. **원장 안전** — 최초 읽기 시 경로별 blob SHA를 기록하고 같은 파일의 동시 변경을 감지한다. 생성한 불변 커밋의 트리에서 파일별 blob SHA를 검증한다. 이 검증만으로 기록 유실을 방지할 수 없으므로 원장은 별도의 병합 정책이 필요하다. 원장(`forecast_history/…`)만 단독 커밋할지는 노트북 단계(④)에서 정한다.
5. **Pages 재빌드 요청 유지** — `GITHUB_TOKEN`으로 만든 커밋은 Pages 자동 빌드를 유발하지 않으므로 `monthly-longterm.yml`의 명시적 `POST pages/builds`를 유지한다. 최종 발행 성공 후 한 번 요청한다. 대체 배포 경로를 실제로 검증한 뒤에만 제거한다.

## 테스트

가짜 API(urlopen 대체)로:
- 여러 파일 → blob N 개, tree 1, commit 1, ref 1 호출.
- ref 경합(422) → 최신 base 로 재구성·재시도, 앞 시도의 부분 반영 없음.
- 블록 밖 `publish()` 는 기존처럼 즉시 커밋(회귀).
- 예외로 블록을 빠져나가면 커밋하지 않음.
- 커밋 후 blob sha 검증이 불일치를 잡음.
- 토큰 문자열이 로그·예외 메시지에 나오지 않음.

## 기대 효과와 위험

- 커밋 하루 400~600 → 60~100 개 추정. Pages 취소 대부분 제거. push 경합 감소.
- 요청 수는 비슷하다(파일당 blob 요청). GITHUB_TOKEN 레이트 리밋(시간당 1,000) 안쪽.
- 배치가 한 번 실패하면 그 실행의 파일이 전부 안 올라간다 → 지난 보고서가 그대로 남는다(현재 원칙과 같음).


## 검토 보완 사항 — 2026-09-23

상태: 문서 검토 반영. 아래 항목은 구현 완료를 뜻하지 않는다. 기존 계획과 충돌하는 경우 이 절의 안전 조건을 우선한다.

### 필수 안전 조건

1. **같은 파일의 동시 변경을 보호한다.** 최신 base_tree를 사용하는 것만으로는 충분하지 않다. 두 실행이 같은 원장을 읽은 뒤 각각 기록을 추가하면, 늦게 저장하는 실행의 오래된 전체 내용이 먼저 추가된 기록을 덮어쓸 수 있다. 최초 읽기 시점의 경로별 blob SHA와 최신 SHA를 비교한다. 다른 파일만 바뀐 경우에는 재시도하고, 같은 파일이 바뀐 경우에는 최신 원장에 안정적인 레코드 키로 병합하거나 안전하게 중단한다. 저장 후 해시 일치는 오래된 내용의 덮어쓰기까지 성공으로 판정하므로 병합 정책을 대신하지 못한다.
2. **HTML 부분 갱신을 보존한다.** `refresh_longterm_tab.publish_tab()`은 충돌할 때 최신 HTML을 다시 읽고 장기 전망 영역만 재적용한다. 배치 이행 후에도 이 동작을 유지한다. 해당 함수는 공통 `publish()` 대신 직접 API를 호출하므로 컨텍스트만 추가해서는 배치에 포함되지 않는다.
3. **Pages 배포를 유지한다.** 현재 토큰과 발행 방식에서는 커밋 감소가 자동 배포를 보장하지 않는다. 최종 발행 뒤 명시적인 빌드 요청을 유지하고 실제 웹 보고서 갱신까지 확인한다.
4. **검증 대상은 생성한 커밋으로 고정한다.** 커밋 후 최신 ref에서만 내용을 비교하면 다른 실행의 정상적인 후속 변경도 오류로 볼 수 있다. 생성한 커밋의 트리를 검증하고, 필요하면 현재 브랜치에 해당 커밋이 포함되어 있는지 별도로 확인한다.

### 구현 범위와 성공 처리

- `ContextVar`는 프로세스 간에 공유되지 않는다. 현재 실적 전망 생성·장기 전망 생성·탭 갱신은 별도 명령이다. 1차 목표는 도구별 배치이며, 전체 워크플로의 원자적 발행이 필요하면 결과물과 manifest를 모은 뒤 마지막 단계에서 일괄 발행하는 구조를 별도로 설계한다.
- 기존 `publish()`는 문서 설명과 달리 content blob SHA 앞 7자를 반환한다. 배치 대기 중에는 최종 커밋 SHA나 성공을 반환할 수 없으므로 반환값 계약과 호출부 로그를 명확히 한다. 대기 상태는 '발행 대기', 최종 ref 갱신·검증 성공 후에만 '발행 완료'로 표시한다.
- 블록 밖으로 전파된 예외만 감지해서는 내부에서 잡고 넘긴 오류를 알 수 없다. 필수 결과물과 선택적 캐시를 구분하고, 필수 파일 생성 실패 시 배치를 중단하는 정책을 명시한다.
- 동일한 blob은 제외한다. 변경 파일이 없는 배치는 커밋과 Pages 요청을 생략한다.
- 409/422를 모두 경합으로 간주하지 않는다. 최신 HEAD와 오류 응답으로 재시도 가능한 경합을 확인하고, 유효성 검사·권한 오류는 실패 처리한다.
- ref 갱신 응답이 유실된 경우 서버에서는 이미 반영됐을 수 있다. 재시도 전 생성한 커밋의 반영 여부를 확인해 중복 커밋을 방지한다.

### 기존 유실 위험 (배치와 무관하게 지금 있다)

- `github_pages.publish()` 와 노트북 `github_put()` 은 409/422 때 sha 만 다시 읽고 **자기 전체 내용으로 다시 덮어쓴다.** 독스트링은 "파일 전체를 덮어쓰므로 재시도가 안전하다" 고 하지만, 다른 실행이 그 사이 행을 추가했다면 그 행이 지워진다.
- `forecast_history/<target>/forecast_log.csv`(와 daily_forecast_comparison·forecast_accuracy_summary)를 **오후 갱신**(`build_afternoon_update.py`, concurrency 그룹 `afternoon-report`)과 **일일 보고서 노트북**(그룹 `daily-report`)이 둘 다 쓴다. 그룹이 달라 동시에 돌 수 있다.
- 두 실행이 겹치면 늦게 쓴 쪽이 먼저 추가된 기록을 지운다. 시간대(오후 갱신 09:37·16:10 KST, 일일 기록 06~09·17~23 KST)가 대체로 어긋나 확률은 낮지만, 원장은 이 저장소에서 가장 중요한 자산이다.

### 제안 (결정 대기)

1. **원장 유실 방지를 배치와 별개로 먼저.** 가장 간단한 대책: 원장을 쓰는 워크플로(일일 보고서·오후 갱신·채점)를 같은 concurrency 그룹으로 묶는다. 워크플로당 한 줄이며 실행이 서로 기다리게 되는 것이 비용이다. 근본 대책(충돌 시 최신 원장을 다시 읽어 레코드 키로 병합)은 배치 ④단계에서 한다.
2. `publish()` 독스트링을 실제 반환값(blob SHA)과 재시도의 한계(전체 덮어쓰기)에 맞게 고친다.
3. 효과 목표는 "도구 단위 커밋"으로 다시 적고, 수치는 ① 이행 후 실측으로 정한다.
